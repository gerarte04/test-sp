# AI-помощник для подготовки товарных описаний

Прототип сервиса, который по данным о контрольно-измерительном приборе собирает **черновик
карточки товара** для B2B-интернет-магазина:

- SEO-заголовок (до 70 символов);
- SEO-описание (800–1200 символов);
- структурированный список ключевых характеристик (с источником каждого значения);
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор и какие задачи решает;
- список того, что нужно уточнить, и замечания автоматической проверки.

Есть веб-форма (поля или JSON) и CLI. Результат — Markdown и JSON, удобные для копирования.

## Быстрый старт

Нужен Python 3.10+.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # и впишите ключ в ANTHROPIC_API_KEY
```

### Веб-форма

```bash
python -m app serve                # http://127.0.0.1:8000
```

Заполните поля (или вставьте JSON на вкладке «JSON») и нажмите «Сгенерировать». Каждый блок
результата копируется отдельной кнопкой, вся карточка — в Markdown или JSON.

### Командная строка

```bash
# оба товара из примера → Markdown и JSON в каталог out/
python -m app generate examples/inputs/products.json --format both --out out/

# один товар, результат в stdout
python -m app generate examples/inputs/incomplete.json

# проверить вход и посмотреть итоговый промпт без обращения к LLM (ключ не нужен)
python -m app generate examples/inputs/products.json --dry-run

# чтение из stdin, подробный лог попыток и проверок
cat product.json | python -m app -v generate -
```

Коды выхода: `0` — успех, `1` — ошибка входных данных, `2` — ошибка LLM API, `3` — ошибка
конфигурации (например, не задан ключ).

### HTTP API

`POST /api/generate` — тело: JSON товара. Ответ `200`: `{"card": {...}, "markdown": "..."}`.
Ошибки: `400` — некорректный вход (с перечнем проблем в `details`), `502` — ошибка LLM API,
`500` — ошибка конфигурации.

### Тесты

```bash
pytest
```

Тесты не обращаются к реальной модели: используется заглушка LLM и `httpx.MockTransport`.

## Формат входных данных

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Файл для CLI может содержать один объект или список объектов.

| Поле | Обязательно | Если нет |
|---|---|---|
| `name` | да | ошибка — без названия карточку не собрать |
| `specs` или `description` | хотя бы одно | ошибка «недостаточно данных» |
| `manufacturer` | нет | в характеристиках «данных нет», пункт в «Требует уточнения» |
| значение характеристики | нет | `""`, `"-"`, `"н/д"`, `null` считаются пустыми → «данных нет» |

Неизвестные поля игнорируются (с пометкой в результате), неверные типы и битый JSON дают понятное
сообщение с указанием строки и столбца.

## Настройка LLM

Ключи и параметры задаются только через переменные окружения или файл `.env` (он в `.gitignore`).
Шаблон — `.env.example`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_PROVIDER` | `anthropic` | `anthropic` или `openai` (любой OpenAI-совместимый API) |
| `ANTHROPIC_API_KEY` | — | ключ Anthropic |
| `ANTHROPIC_MODEL` | `claude-sonnet-5-5` | модель Anthropic |
| `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL` | — / OpenAI / `gpt-4o-mini` | OpenAI, Ollama, LM Studio, vLLM… |
| `LLM_TIMEOUT` | `60` | таймаут запроса, с |
| `LLM_MAX_ATTEMPTS` | `2` | сколько раз модель может переписать ответ, не прошедший проверки |
| `LLM_TEMPERATURE` | `0.2` | температура (только для OpenAI-совместимого API) |

Основной провайдер — Anthropic. Поддержка OpenAI-совместимого API добавлена, чтобы прототип можно
было запустить на локальной модели без внешнего ключа, например через Ollama:

```bash
LLM_PROVIDER=openai OPENAI_BASE_URL=http://localhost:11434/v1 OPENAI_MODEL=qwen2.5:14b OPENAI_API_KEY=ollama python -m app serve
```

## Примеры

- `examples/inputs/products.json` — два товара: манометр DM 02 (из задания) и преобразователь
  давления ПД100И (с намеренно пустым «напряжением питания» и характеристиками, которые есть
  только в описании).
- `examples/inputs/incomplete.json` — неполные данные (нет производителя, описания, пустой класс точности).
- `examples/inputs/invalid.json` — битый JSON.
- `examples/outputs/` — результаты для двух товаров (`.md` и `.json`) и вывод CLI для битого JSON.

## Как устроено

```
вход (JSON / форма)
  → input_validation   разбор, нормализация, отчёт о пропусках
  → prompts            system-промпт с правилами + данные в <product_data>
  → llm                Anthropic (tool use) или OpenAI-совместимый API (JSON mode)
  → guards             проверки ответа кодом
  → service            повторная генерация с перечнем ошибок, сборка карточки
  → render / web / cli Markdown, JSON, HTML
```

| Файл | Что внутри |
|---|---|
| `app/input_validation.py` | проверка входа, типовые характеристики КИП, отчёт о пропусках |
| `app/prompts.py` | system-промпт, JSON-схема ответа, промпты для первой и повторной попытки |
| `app/llm.py` | клиенты LLM, перевод ошибок API в понятные сообщения |
| `app/guards.py` | проверки против выдуманных данных и проверки длины |
| `app/service.py` | оркестрация, сборка списка характеристик |
| `app/render.py` | Markdown-представление |
| `app/web.py`, `app/static/index.html` | FastAPI + одностраничная форма без сборки |
| `app/cli.py` | командная строка |

## Промпты и принятые решения

**1. Защита от выдуманных характеристик — в три слоя.**

- *Промпт.* System-промпт прямо запрещает использовать знания о производителе и модельном ряде,
  перечисляет то, что модели обычно «дорисовывают» (IP, ГОСТ, реестр СИ, поверка, материалы,
  температура, гарантия…), запрещает расшифровывать обозначение модели и требует переносить числа
  буквально. Пропущенное не замалчивается, а попадает в `clarifications`.
- *Таблицу характеристик собирает код, а не модель.* Значения берутся из `specs` как есть,
  отсутствующие типовые характеристики (диапазон, точность, питание, корпус, интерфейсы)
  и пустые поля помечаются «данных нет». У каждой строки указан источник.
- *Проверка ответа кодом* (`guards.py`):
  - каждое число в заголовке, описании, запросах и блоке для менеджера должно встречаться во
    входных данных (с нормализацией `1,6` = `1.6`, `02` = `2`);
  - «рискованные» термины (ГОСТ, IP, поверка, сертификат, Modbus, RS-485, материалы…) допустимы,
    только если они есть во входе;
  - характеристики, которые модель извлекла из описания, принимаются только с дословной цитатой,
    которая действительно есть в описании, и числа значения должны совпадать с цитатой.

**2. Повтор с обратной связью.** Если ответ не прошёл проверки, модель получает исходные данные,
свой предыдущий ответ и конкретный список проблем («в SEO-описании есть число 60, которого нет во
входных данных», «описание 640 символов, нужно 800–1200»). Если и после последней попытки проблемы
остались, карточка всё равно возвращается, но со статусом `needs_review` и списком замечаний —
контент-менеджер видит, что именно проверить. Неподтверждённые характеристики из таблицы удаляются,
слишком длинный заголовок аккуратно сокращается по границе слова.

**3. Структурированный ответ.** Для Anthropic используется принудительный вызов инструмента
(`tool_choice`) с JSON Schema — модель не может ответить свободным текстом. Для OpenAI-совместимых
API — JSON mode и схема в промпте, плюс терпимый парсер (снимает ```json-обёртку). Ответ
валидируется Pydantic-моделью.

**4. Данные отделены от инструкций.** Данные товара передаются внутри `<product_data>`, и промпт
указывает, что текст внутри — это данные, а не команды (защита от «инструкций» в описаниях
поставщиков).

**5. Пробелы во входе передаются модели.** Список найденных кодом пропусков добавляется в промпт,
чтобы модель не пыталась их «заполнить» и учла их в `clarifications`.

**6. Требования к текстам.** Заголовок — по формуле «тип + модель + ключевой параметр +
производитель», без «купить/цена/лучший». Описание — 2–3 абзаца: назначение, характеристики,
применение (только если следует из описания). Запросы — реалистичные, в нижнем регистре, разных
типов (модель, параметр, производитель, коммерческий). Блок для менеджера — 2–4 пункта
«кому подходит» и «какие задачи решает».

## Ограничения и возможные улучшения

Ограничения:

- Проверка «выдумок» эвристическая: ловит числа и типовые термины, но не смысловые утверждения без
  чисел («подходит для агрессивных сред»). Такие места остаются на вычитку.
- Проверяется наличие числа во входе, но не его привязка: модель теоретически может приписать
  верное число не той характеристике.
- Список типовых характеристик общий для КИП. Для механического манометра строки «Питание» и
  «Интерфейсы» будут помечены «данных нет», хотя для такого прибора они неприменимы.
- Длина SEO-полей проверяется в символах; оценки поисковой частотности запросов нет — это
  предположения модели, а не данные из Wordstat.
- Нет кэша, очереди и ограничения частоты запросов; генерация синхронная (один товар — один-два
  запроса к модели).

Что можно улучшить:

- Профили категорий (манометры, датчики, расходомеры, термометры) со своим набором обязательных
  характеристик и понятием «неприменимо».
- Второй проход «LLM-критик» для проверки смысловых утверждений текста против входных данных.
- Привязка чисел к характеристикам (сопоставление «число + единица» с конкретным полем `specs`).
- Разбор PDF-паспорта на входе, пакетная обработка CSV/XLSX, выгрузка в формат CMS.
- Подбор запросов по данным Яндекс Wordstat; учёт уже существующих карточек, чтобы избежать
  дублирования текстов.
- Набор эталонных товаров и автоматическая оценка качества промпта (регрессионные тесты на
  реальной модели).
